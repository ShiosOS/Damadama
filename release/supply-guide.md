# Supply evidence reference

The supply modules connect one paired production build to original scan evidence, immutable publication, isolated signing, and repeated staging and promotion admission. The shared CI graph is implemented in this source. Production activation remains closed pending postmerge main execution and exact-head native acceptance.

## Archive assessment

`scanArchive({ archivePath, build, source, authority, evidenceDirectory, frontendBuildDirectory? })` accepts the existing application build record. It requires source and controller equality and checks the archive hash before and after native Syft and Grype execution. It requires a fresh evidence directory. It returns an unsigned scan assessment and writes an archive mirror, the complete runtime SPDX 2.3 inventory, raw Grype reports, authored scanner config, policy, normalized decision, and assessment. With `frontendBuildDirectory`, it reconstructs the retained web and final archives and scans their installed npm inventory in the same scanner lifetime. Runtime and frontend findings form one tagged union with one exception registry. Each normalized finding retains every raw report and match index. A vulnerability decision is `accepted` or `refused`. Tool failures, malformed output, and unavailable databases throw errors. A persisted `accepted` decision has no authority when reread.

The committed policy blocks High and Critical vulnerabilities, including unfixed findings. Lower findings remain in the raw report and normalized findings. Exceptions must match the vulnerability namespace and ID, PURL, installed version, and exact image scope. Each exception requires an owner, reviewer, reason, repository issue, and unexpired UTC timestamp. Broad, duplicate, malformed, expired, and unmatched exceptions refuse assessment. The initial exception list is empty.

The scanner updates one database in a new isolated cache, then disables auto-update for both image and npm scans. Native database metadata and the actual database file hash must remain equal before and after each Grype operation. The assessment records each scan start and end time and uses the earliest runtime start for age checks. The scanner uses an explicit config and an allowlisted environment. User config, ignore rules, VEX inputs, severity filters, credentials, and environment suppression settings are not inherited. The effective pinned profile includes four native kernel-header ignore rules. The validator checks the complete observed effective profile with only the private cache path normalized. Unknown profile changes or any ignored matches refuse assessment. Scanner binaries and downloaded archives have committed SHA-256 pins. The installer verifies Anchore checksum bundles with pinned Cosign and the exact release workflow identity before installing either scanner.

Scans expire after 24 hours. Databases expire after five days. Verification checks both against the current clock, then downloads the current upstream database in isolation and compares its exact schema, build time, and SHA256 with the scanned database. A mismatch reports only those validated expected and observed identities. A changed database refuses the existing candidate. This controller does not implement a rescan or reissue lifecycle. Database availability is required.

## Signed manifest

`verifyRelease({ expectedSource, expectedAuthority, expectedImage, evidenceDirectory })` calls the pinned native GitHub CLI itself. It accepts no verification-result JSON or trust override. It verifies the manifest file signature and requires schema 2. schema 1 and incomplete frontend capsules refuse. It hashes every fixed role, authenticates and downloads the original producer ZIPs again, compares their build and scan members, reconstructs the frontend independently, re-evaluates policy, and verifies separate standard provenance and runtime SPDX bundles against the actual OCI digest. The SPDX predicate must match the scanned inventory. The image archive hash must match both the signed manifest and expected published image.

The fixed production authority is `ShiosOS/Damadama`, repository ID `1412858535`, owner ID `31512984`, issuer `https://token.actions.githubusercontent.com`, and `.github/workflows/stage.yml@refs/heads/main`. The verifier requires the exact case-sensitive certificate identity and ref, expected source and signer SHAs, source/controller equality, selected run and attempt, a hosted runner, and an authenticated transparency-log or timestamp-authority observation. GitHub CLI 2.102.0 contains the source-ref and signer-workflow matching fixes. The verifier also compares these authenticated fields itself.

The evidence directory contains these files:

- `manifest.json` binds purpose, source, controller authority, actual image identity, immutable producer artifacts, and exact file hashes.
- `manifest.bundle.json` authenticates that file as a standard SLSA file subject.
- `build/` contains the original final and web archives, raw build metadata, build record, builder versions, and release metadata.
- `scan/` contains the archive mirror, runtime and supplemental frontend reports, full frontend observation, authored config, assessment, policy, and decision.
- `signer/provenance.bundle.json` and `signer/sbom.bundle.json` authenticate the OCI subject in production and the original archive in proof. The manifest binds their exact bytes.

Production producer artifacts use `supply-build-<attempt>` and `supply-scan-<attempt>` from successful `build` and `scan` jobs in the authenticated attempt. The stage workflow issues those originals, `published-image-<attempt>` from `publish`, and `supply-release-<attempt>` from `sign`. Missing or expired artifacts refuse verification.

## Production issuance and admission

`publishCandidate(candidate)` authenticates original build and scan artifacts, reconstructs their evidence, and performs native freshness checks before preparation and immediately before and after publication. It proves that the published registry content matches the original archive. Only the publisher writes packages.

`prepareRelease(candidate, directory)` authenticates publication and original producers, validates evidence, and compares registry content. `assembleRelease(candidate, directory)` reacquires originals and publication, repeats validation, and verifies the standard OCI provenance and SPDX bundles before writing manifest schema 2. Neither operation acquires a vulnerability database. The signer uses the fixed GH and Crane profile.

`locateRelease(candidate)` independently selects publication and the complete signed capsule from their successful jobs and returns `{ image, supply }` after full `verifyRelease` authentication. `authenticateRelease(candidate, image, supply)` repeats that work and resolves without a value only when the entire current identity matches the frozen identity. It does not accept a stored verification receipt as authority.

Verified record schema 3 requires `evidence.supply`. Promotion plan schema 2 freezes that same identity, including the attempt-scoped capsule artifact ID, name, ZIP digest and size, signer job ID and name, and manifest hash. Stage receives CI rows from the final native read. Promotion retains its immutable image-reference return value.

`supply-registry.mjs` reads only `ghcr.io/shiosos/damadama` at the expected immutable digest. It hashes raw manifest bytes, accepts finite single-image OCI and Docker schema 2 media types, and rejects indexes, external descriptor URLs, redirects, and unsupported encodings. Configuration bytes must equal the original archive. Each fetched compressed layer must satisfy its own hash and size. Ordered expanded DiffIDs and sizes must match the original layers, so legitimate recompression is accepted without confusing compressed hashes with DiffIDs.

The manifest limit is 64 KiB, the config limit is 1 MiB, and the layer-count limit is 64. Compressed bytes and aggregate expanded bytes each have a 2 GiB limit, with a 1 GiB expanded per-layer limit. Original ZIP bounds remain tighter where applicable. A single registry invocation has a finite deadline and cancels stream reads on expiry.

Registry requests use only the current job's ephemeral `GITHUB_TOKEN` and the fixed GHCR token realm, service, and repository pull scope. Each production OCI signature invocation writes a minimal private Docker configuration inside its isolated home and removes it afterward. Scanner and proof environments do not inherit that credential configuration.

Production build, scan, publication, and capsule artifacts have three-day retention. This is an availability limit. Current-main, deletion, scan age, database age, and exact current-database checks can refuse earlier. The longer-lived record and plan do not replace original evidence or promise a rollback period.

The production CLI reads `candidate.json`. Its exact forms are `publish <directory>`, `prepare <directory>`, `assemble <directory>`, `verify <directory>`, and `upload-paths <directory> <role>`. Upload roles are `build`, `scan`, `publish`, and `release`. The complete capsule upload contains the 22 canonical evidence files plus the manifest and its bundle. Local `producers.json`, `image.json`, and verifier output are not capsule members.

## Native CI proof

The separate `origin-probe` job is an exploratory gate for the frontend extension. It builds two tiny web images with identical visible assets and different hidden markers, exports each to OCI layout and Docker archive in one solve, and checks that their config and rootfs identities agree. It then builds a tiny final image from each immutable named `web` context with the existing `COPY --from=web` mechanism. The validator reads the copied asset bytes from both final Docker archives, requires the returned `pkg:oci/web` material, `context:web` argument, and LLB copy source to agree on the selected OCI descriptor, and refuses the first descriptor when the second context was used. It records both final image descriptors without requiring equality of build timestamps or history. Embedded provenance makes the Docker exporter reject simultaneous exports, so the probe disables embedded attestations and requests max provenance in Buildx's separate metadata file. The exact-head Linux fixture passed both accepted and wrong-context cases in run [39119284524](https://github.com/ShiosOS/Damadama/actions/runs/39119284524). Its metadata reported `completeness.materials=false` and `reproducible=false`; this establishes only the specific named web input, not complete source inventory or a reproducible build. The job retains raw OCI archives, Docker archives, Buildx metadata, and host Docker/Buildx versions for review for three days. The private BuildKit builder uses the official [`moby/buildkit:v0.26.2` tag](https://hub.docker.com/r/moby/buildkit/tags?name=v0.26.2) at index digest `sha256:de10faf919fc71ba4eb1dd7bd6449566d012b0c9436b1c61bfee21d621b009aa`, read from the Docker Hub tag API. The hosted Docker CLI and Buildx are recorded, not pinned. This probe does not grant application frontend coverage or alter the signed proof.

The proof build now exports the real Dockerfile's `web` target once to an OCI layout and Docker archive, checks that their config digest and rootfs DiffIDs agree, and supplies the OCI manifest digest as the named `web` input to one final application build. It retains both web archives, raw Buildx metadata, host versions, the observed Docker CLI hash, and a linked observation record with the application Docker archive for three days. The Buildx plugin binary hash is recorded as unavailable rather than described as pinned. The reconstruction validates the real connected web-to-publish-to-final graph, exact installed package locations, emitted assets, publish compression derivatives, and release metadata. Raw frontend Syft and SPDX inventories must match every retained versioned manifest, including duplicate locations. Each frontend Grype artifact ID joins one validated SPDX package with exact name, version, type, and PURL. Native SPDX-derived finding locations are null. The application scanner keeps its unsigned observation label. Signed verification grants frontend coverage only after reconstructing the original paired build and matching the full observation and raw reports. The production verifier selects the real application contract. Producer text cannot select the tiny fixture contract.

Installed inventory includes both `/src/node_modules` and the web workspace's `/src/web/node_modules`, including scoped packages, nested dependencies, conflicting versions, and versioned helper manifests. Scanner input preserves their exact `/node_modules/...` and `/web/node_modules/...` locations. Root and web workspace manifests and unversioned helpers remain separate path and hash observations. Package roots require nonblank names and versions. Selected hardlinks retain bounded in-image resolution; selected symlinks and malformed manifests refuse coverage.

`supply-chain-proof.yml` uses separate fresh hosted build, fixture scan, application scan, signer, and verifier jobs. Pull requests run unsigned work. Only a push to `codex/polish-image-supply-chain` in this repository can reach the signer. Only the signer receives OIDC and attestation write permissions. Every attestation explicitly disables registry pushes and storage records. No job receives package write permissions, deployment environment credentials, or provider secrets.

The signer independently authenticates the run, successful producer jobs, artifact membership, and artifact ZIP hashes. It streams complete ZIPs under a 1 GiB transport budget, checks metadata size and SHA256, validates the complete fixed central and local member sets, and extracts only registry-owned members. Duplicate, unknown, missing, aliased, overlapping, oversized, and unsupported entries refuse. The expansion budget is 2 GiB per ZIP, 768 MiB per archive member, and 32 MiB per JSON member. Selected output is streamed with exact size and CRC checks. The signer compares the scan mirror with the original builder archive and independently reconstructs both image archives before signing. It installs only pinned GH and Crane and executes no build, scanner, or database update. Assembly repeats original producer authentication, member comparisons, reconstruction, policy checks, and bundle verification before emitting the manifest. The signer produces real GitHub-signed file-subject provenance, SPDX, and manifest bundles. `verifyCIProof` has a separate fixed proof identity and returns `ci-signature-proof`, which cannot authorize production.

The fresh verifier runs native positive verification, then refuses changed archives, manifests, reports, inventories, policies, decisions, bundles, ordinary forged JSON, incorrect source or signer SHAs, incorrect runs or attempts, and proof identity passed to production. Parser fixtures in unit tests are explicitly not cryptographic proof. Native cryptographic acceptance requires a successful run of this workflow at the reviewed SHA.

The unsigned paired fixture gate has its own web OCI and Docker archives, final archive, resolved metadata, installed packages, assets, and independent release metadata. A generated temporary Dockerfile preserves the observed three-step final copy graph. Both variants retain real lodash 4.18.1 at the root installation. The web workspace has a separate lodash installation and duplicate versioned helper, using 4.18.1 in the clean variant and vulnerable 4.17.15 in the other. Three unversioned observations retain the root and web manifests and a workspace helper. The final runtime retains the same is-number 7.0.0 package and six asset files. Downloads use fixed SHA-512 integrity values and execute no package scripts. The gate requires distinct SPDX IDs for all three installed locations, findings joined to the vulnerable workspace paths, a frontend-only refusal, an exact temporary union exception, all malformed exception refusals, and a wrong immutable context refusal despite equal final assets. This corrected fixture shape requires a fresh hosted native run. The signed subject uses paired-clean exclusively and retains its own complete build and scan groups. The original runtime-only fixtures remain unsigned policy controls.

`supply-evidence.mjs` owns the fixed build, scan, and signer roles, manifest paths, original producer layouts, and upload paths. `supply-proof.mjs upload-paths` emits those paths directly to the workflow step output. Original build members remain distinct from scanner output. schema 2 binds nine `build/` files, eleven `scan/` files including the explicit archive mirror and supplemental frontend reports, and two standard bundles under `signer/`. Its signature bundle remains outside self-hashing. Every bound file is exercised by the hosted cryptographic tamper matrix. The signer also waits for the independent application scan to succeed.

The vulnerable fixture inventories lodash 4.17.15 and requires the intended command-injection advisory. The clean fixture inventories the published [lodash 4.18.1](https://registry.npmjs.org/lodash/4.18.1) release. The earlier 4.17.21 fixture now has a High advisory and cannot serve as a clean baseline. Native fixture checks also exercise exact temporary exceptions and expired, broad, and malformed refusals. Those exceptions never enter the committed policy. The application scan runs independently and fails visibly on policy refusal. Its findings are retained even when the synthetic cryptographic proof succeeds.

## Coverage and activation limits

The final application inventory must contain OS and .NET package identifiers. Compiled frontend assets do not expose their installed dependency graph. Unsigned scans remain incomplete evidence. Mandatory schema 2 verification reconstructs the named web-stage inventory and final assets from independently authenticated originals and checks exact Syft/SPDX inventories and Grype joins. It preserves every duplicate package location and unversioned manifest. Production requires the real application origin and .NET asset mapping, OS and .NET inventory, current policy, current database, and fixed stage/main signatures. The native signed proof uses a separate tiny contract and cannot authorize production. The new schema 2 cryptographic matrix requires an exact-head hosted run before acceptance.

The prior schema 2 push at dcc2a09 passed build, paired and application scans, and signing. Its fresh verifier refused current database equality before genuine acceptance and tamper enumeration. That run did not log the observed database hash, so the cause remains undiagnosed. Local parser and policy controls do not establish fresh native signing or cryptographic acceptance. The corrected inventory, paired fixture, and diagnostics require a new exact-head build, scan, sign, and verify matrix.

The proof workflow retains actual application archives for three days. Reports, proof bundles, and the tiny synthetic fixture archives remain available for 90 days. Application scan output also contains an image mirror. The original build artifact remains the authority for build membership and expires after three days. This does not establish a 90-day rollback support window. Artifact membership checks also refuse once producer build artifacts expire after three days. Future release integration must retain accessible exact bytes and authenticated evidence for every supported rollback candidate.

Production integration now composes the existing approval, current-main, source, digest, and recovery controllers. Native package authorization, production OCI signatures, bounded registry compatibility, and cold preflight feasibility remain unproved. The shared CI graph changes await composition with the landed CI policy. The separate proof workflow cannot establish production acceptance.

## Local commands

`node release/supply-install.mjs` installs authenticated Linux x64 or Windows x64 tools into ignored `.audit/supply-tools`. Fixed `scanner`, `signer`, and `verifier` scopes install only each job's tools. All scopes use the same committed archive and executable pins. The signer scope contains GH and Crane; the verifier also installs Grype and its Cosign authentication dependency.

`node --test release/supply-chain.test.mjs` runs deterministic boundary and policy tests without native signing.

`node release/supply-origin-probe.mjs .audit/origin-probe` runs the small origin experiment on a Linux Docker host. A passing parser unit test alone does not establish the native Buildx metadata shape.

`node release/supply-native.mjs .audit/supply-native` creates and scans the clean and vulnerable Docker-save fixtures without a Docker engine. It requires network access for the current vulnerability database.

`node --test release/*.test.mjs` runs the release test suite. `bun run check` remains the repository handoff gate and requires a working Docker engine.
